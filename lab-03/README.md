## Завдання 2. Монітор доступності API

### Призначення

`api_monitor.py` — Python-інструмент для перевірки доступності HTTP/HTTPS endpoint'ів.

Програма перевіряє кожну ціль із конфігураційного файлу, вимірює час відповіді та визначає тип проблеми. Вона розрізняє DNS-помилки, відхилення з'єднання, тайм-аути, помилки TLS-сертифіката, неочікувані HTTP-статуси та повільні відповіді.

Результати зберігаються у структурованому JSON-файлі. Інформація про виконання записується в журнал. За наявності змінної середовища `MONITOR_WEBHOOK_URL` програма може надсилати сповіщення про проблемні endpoint'и.

### Структура файлів

```text
lab-03/
├── README.md
├── api_monitor.py
└── config/
    └── endpoints.json
```

Під час роботи програма автоматично створює `api_monitor.log` і `api_monitor_results.json`. Це файли результатів виконання, а не вихідний код.

### Конфігурація

Для налаштування endpoint'ів використовується JSON-файл `config/endpoints.json`.

Приклад:

```json
{
  "targets": [
    {
      "name": "Working endpoint",
      "url": "https://example.com/",
      "expected_status": 200,
      "timeout": 5,
      "slow_threshold": 2
    },
    {
      "name": "Unexpected status",
      "url": "https://example.com/not-found",
      "expected_status": 200,
      "timeout": 5,
      "slow_threshold": 2
    }
  ]
}
```

Параметри:

- `name` — назва цілі;
- `url` — адреса endpoint'а;
- `expected_status` — очікуваний HTTP-статус;
- `timeout` — максимальний час очікування відповіді в секундах;
- `slow_threshold` — поріг часу відповіді в секундах, після якого відповідь вважається повільною.

Конфігурація відокремлена від програмного коду, тому адреси та параметри endpoint'ів можна змінювати без редагування Python-скрипту.

### Запуск програми

З каталогу `lab-03`:

```powershell
python api_monitor.py --config config/endpoints.json
```

Перегляд доступних параметрів:

```powershell
python api_monitor.py --help
```

Збереження результатів в окремий файл:

```powershell
python api_monitor.py --config config/endpoints.json --output results.json
```

Параметр `--config` є обов'язковим. Параметр `--output` необов'язковий; за замовчуванням результати зберігаються в `api_monitor_results.json`.

### Типи помилок

#### DNS

Виникає, коли доменне ім'я не вдається перетворити на IP-адресу.

Тип помилки: `DNS`.

#### Connection refused

Виникає, коли спробу встановити TCP-з'єднання відхилено, наприклад, через відсутність сервісу на вказаному порту.

Тип помилки: `CONNECTION_REFUSED`.

#### Timeout

Виникає, коли відповідь не надходить у межах установленого часу очікування.

Тип помилки: `TIMEOUT`.

#### Certificate error

Виникає, коли перевірка TLS-сертифіката HTTPS endpoint'а не проходить.

Для тестування використовується `https://expired.badssl.com/` — тестовий endpoint із простроченим сертифікатом.

Тип помилки: `CERTIFICATE_ERROR`.

#### Unexpected HTTP status

Виникає, коли сервер повертає HTTP-статус, який не збігається з `expected_status`. Наприклад, очікується `200`, але сервер повертає `404`.

Тип помилки: `UNEXPECTED_STATUS`.

#### Slow response

Виникає, коли відповідь надійшла з очікуваним HTTP-статусом, але час відповіді перевищив `slow_threshold`.

Тип помилки: `SLOW_RESPONSE`.

### Повторна спроба

Для мережевих помилок програма виконує одну повторну спробу. До них належать DNS-помилки, відхилення з'єднання, тайм-аути, помилки сертифіката та інші мережеві помилки.

Неочікуваний HTTP-статус і повільна відповідь повторно не перевіряються, оскільки HTTP-відповідь уже отримано.

Приклад:

```text
[RETRY] DNS failure | перша спроба: DNS
[PROBLEM] DNS failure | DNS | ...
```

### Структуровані результати

Результати за замовчуванням зберігаються у `api_monitor_results.json`.

Файл містить загальний час запуску `check_time` і список `results`. Для кожної цілі зберігаються:

- `time` — час формування результату перевірки;
- `target` — назва цілі;
- `url` — адреса endpoint'а;
- `status` — `OK` або `PROBLEM`;
- `response_time` — тривалість перевірки в секундах;
- `failure_type` — тип помилки або `null`, якщо помилки немає;
- `details` — HTTP-статус або додаткові відомості про проблему.

Приклад результату:

```json
{
  "check_time": "2026-10-13 15:00:00",
  "results": [
    {
      "time": "2026-10-13 15:00:01",
      "target": "Working endpoint",
      "url": "https://example.com/",
      "status": "OK",
      "response_time": 0.588,
      "failure_type": null,
      "details": "HTTP 200"
    }
  ]
}
```

Час і тривалість у прикладі наведено для ілюстрації. Реальні значення залежать від запуску.

### Логування

Журнал роботи зберігається у `api_monitor.log`.

Записи містять час, рівень повідомлення (`INFO`, `WARNING` або `ERROR`) та опис дії чи результату.

Логування допомагає відстежувати запуск програми, результати перевірок, мережеві помилки, повторні спроби та проблеми з webhook.

### Сповіщення через webhook

URL webhook передається через змінну середовища `MONITOR_WEBHOOK_URL` і не зберігається безпосередньо в коді чи JSON-конфігурації.

Приклад встановлення змінної у PowerShell:

```powershell
$env:MONITOR_WEBHOOK_URL="WEBHOOK_URL"
```

Замість `WEBHOOK_URL` потрібно вказати власну адресу webhook, не публікуючи її у репозиторії.

За наявності налаштованого webhook програма намагається надіслати повідомлення для кожної проблемної цілі. Повідомлення містить тип збою, назву endpoint'а, URL і подробиці помилки. Поточний формат повідомлення сумісний із Discord webhook; для інших платформ формат запиту може потребувати змін.

Якщо змінну середовища не задано, сповіщення не надсилається, а відповідна інформація записується в лог.

### Коди завершення

- `0` — усі перевірені endpoint'и працюють нормально;
- `1` — помилка конфігурації або запису результатів;
- `2` — виявлено проблему хоча б з одним endpoint'ом.

Ці коди дають змогу іншим скриптам або CI-системам визначати результат виконання монітора.

### Тестування

Для перевірки програми використовуються такі сценарії:

| Тест                                                  | Очікуваний результат                                                |
| ----------------------------------------------------- | ------------------------------------------------------------------- |
| `https://example.com/`                                | `OK`, якщо повернуто HTTP 200 і відповідь не повільна               |
| Неіснуючий домен                                      | `DNS`                                                               |
| `http://127.0.0.1:59999/`                             | Зазвичай `CONNECTION_REFUSED`, якщо порт не слухається              |
| `http://10.255.255.1/`                                | Тестовий сценарій `TIMEOUT`; результат залежить від мережі          |
| `https://expired.badssl.com/`                         | `CERTIFICATE_ERROR`, якщо перевірка сертифіката доходить до сервера |
| `https://example.com/not-found`                       | Зазвичай `UNEXPECTED_STATUS`, якщо сервер повертає HTTP 404         |
| `https://example.com/` із дуже малим `slow_threshold` | `SLOW_RESPONSE`, якщо тривалість перевищує поріг                    |

Результат мережевих тестів може залежати від стану мережі, DNS, проксі та налаштувань безпеки. Для тесту повільної відповіді поріг задається дуже малим, щоб продемонструвати класифікацію `SLOW_RESPONSE`.

### Connection refused та timeout

`Connection refused` означає, що з'єднання було відхилено. Спочатку варто перевірити, чи запущений потрібний сервіс і чи слухає він правильний порт.

`Timeout` означає, що відповідь не надійшла за відведений час. Варто перевірити мережевий шлях, firewall, маршрутизацію, доступність вузла та навантаження сервера.

Отже, ці типи помилок потребують різних напрямків діагностики: для `CONNECTION_REFUSED` насамперед перевіряють сервіс і порт, а для `TIMEOUT` — також мережеве з'єднання та доступність сервера.
